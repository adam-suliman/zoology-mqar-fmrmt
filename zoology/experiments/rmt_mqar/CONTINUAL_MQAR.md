# Continual MQAR Experiments

This document explains the continual-learning MQAR setup in this folder. The
main experiment file is `continual_vocab.py`.

## Goal

The goal is to turn MQAR into a sequential continual-learning task. Instead of
training independent models on independent static MQAR datasets, one model is
trained through a sequence of stages. Each stage introduces a new disjoint
key/value vocabulary range. After each training stage, the model is evaluated on
all stages it has seen so far.

This is closer to an incremental-classification setup than the static
`capacity_sweep.py` or `context_sweep.py` experiments:

```text
stage 0 train -> evaluate stage 0
stage 1 train -> evaluate stages 0, 1
stage 2 train -> evaluate stages 0, 1, 2
stage 3 train -> evaluate stages 0, 1, 2, 3
```

The model weights and optimizer state persist across stages.

## Task Definition

Data is generated by `IncrementalMQARConfig` in
`zoology/data/incremental_mqar.py`.

Each example is a standard MQAR-style sequence:

```text
key_1 value_1 key_2 value_2 ... key_K value_K ... query_key ... query_key ...
```

The label at each query position is the value associated with the queried key.
Non-query positions use label `-100`, so they are ignored by cross-entropy loss
and accuracy.

For continual MQAR, each stage owns a disjoint key range and value range:

```text
lower half of vocab: key tokens
upper half of vocab: value tokens

stage 0:
  keys   [key_start_0, key_end_0)
  values [value_start_0, value_end_0)

stage 1:
  keys   [key_start_1, key_end_1)
  values [value_start_1, value_end_1)

...
```

For stage `s`, keys are sampled only from that stage's lower-half key range, and
values are sampled only from that stage's upper-half value range. Labels only use
that stage's value range.

With `random_non_queries=True`, zero filler tokens are replaced by random
distractor tokens sampled from the current stage's key and value ranges. This
prevents future-stage token leakage through distractors.

## Default Continual Vocab Setup

`continual_vocab.py` currently uses:

```text
num_stages = 4
vocab_size = 2048
keys_per_stage = 128
values_per_stage = 128
num_kv_pairs = 8
input_seq_len = 128
train examples per stage = 1,000
test examples per stage = 256
max_epochs = 4 per stage
batch_size = 32
segment_len = 64 for RMT models
```

The three compared models are created by `comparison_models()` in `_common.py`:

```text
attention
base_rmt
fast_memory_rmt
```

## Training Loop

The launcher dispatches `ContinualTrainConfig` to `train_continual()` in
`zoology/train.py`.

The training loop does this:

```text
build one model once
build one train/test dataloader pair per stage
initialize one optimizer once

for each stage:
  optionally evaluate the current stage before training it
  train on that stage for max_epochs
  evaluate every seen test stage
  log seen-stage metrics, plasticity, BWT, FWT, forgetting, and timing
```

The optimizer is not recreated between stages. That means optimizer momentum and
weight state carry across stages, matching a standard continual-learning setup.

For Fast Memory RMT specifically:

```text
fast_memory_tokens:
  updated manually after loss.backward()

general model weights + initial_memory_tokens:
  updated by AdamW according to rmt_slow_update_freq
```

With current defaults, `reset_memory_each_batch=True`, so fast memory is reset
from slow memory at the start of each batch.

## Metrics

Each stage evaluation logs:

```text
continual/stage_{i}/accuracy
continual/stage_{i}/loss
continual/stage_{i}/forgetting
continual/stage_{i}/learning_accuracy
continual/stage_{i}/bwt
continual/stage_{i}/forgetting_from_learning
```

The aggregate metrics are:

```text
continual/stage
continual/seen_avg_accuracy
continual/avg_forgetting
continual/avg_forgetting_from_learning
continual/current_stage_accuracy
continual/plasticity
continual/avg_learning_accuracy
continual/plasticity_drop_from_stage_0
continual/avg_bwt
```

Stage-level compute and timing metrics are also logged on the same continual
summary record:

```text
continual/stage_train_wall_seconds
continual/stage_train_examples
continual/stage_train_tokens
continual/stage_train_batches
continual/stage_optimizer_steps
continual/stage_train_examples_per_second
continual/stage_train_tokens_per_second
continual/stage_seen_eval_wall_seconds
continual/stage_seen_eval_examples
continual/stage_seen_eval_tokens
continual/stage_seen_eval_batches
continual/stage_seen_eval_examples_per_second
continual/stage_seen_eval_tokens_per_second
continual/stage_wall_seconds
continual/cumulative_train_wall_seconds
continual/cumulative_seen_eval_wall_seconds
continual/cumulative_wall_seconds
```

The token counts are processed input-token counts, not hardware FLOP estimates.
For training, examples, tokens, and batches include all epochs for that stage.
`stage_optimizer_steps` reflects the slow-update cadence used by models such as
FMRMT. For seen validation, examples, tokens, and batches include the test splits
for all stages evaluated after the current training stage. On CUDA, the trainer
synchronizes before and after timed training/evaluation blocks so wall-clock
measurements include queued GPU work.

Plasticity is the current stage's accuracy immediately after training that
stage:

```text
plasticity_t = accuracy(stage_t test after training stage_t)
```

This is intentionally separate from old-stage accuracy after later training.
Low final accuracy on an old stage is counted as forgetting or negative BWT,
not as loss of plasticity. Loss of plasticity should be inferred only when
`learning_accuracy` / `current_stage_accuracy` declines for newly trained
stages.

Best-accuracy forgetting is computed against the best previous accuracy for
that stage:

```text
forgetting_i = max(0, best_previous_accuracy_i - current_accuracy_i)
```

Forgetting from learning is computed against the accuracy obtained immediately
after that stage was trained:

```text
forgetting_from_learning_i = max(0, learning_accuracy_i - current_accuracy_i)
```

BWT is the signed version of the same comparison:

```text
bwt_i = current_accuracy_i - learning_accuracy_i
```

Negative BWT indicates forgetting. Positive BWT means later training improved an
old stage.

Seen average accuracy is the mean accuracy across all test stages seen so far:

```text
seen_avg_accuracy = mean(stage_0_accuracy, ..., current_stage_accuracy)
```

If `evaluate_future_stages=True`, the trainer also evaluates stages before they
are trained. This logs:

```text
continual/stage_{i}/pre_learning_accuracy
continual/stage_{i}/fwt_from_random
continual/stage_{i}/fwt_from_initial
continual/avg_fwt_from_random
continual/avg_fwt_from_initial
```

`pre_learning_accuracy` is the score on stage `i` before training stage `i`.
`fwt_from_random` subtracts the stage's random baseline when the data config
exposes one. `fwt_from_initial` subtracts the untrained model's score on the
same stage. These are the forward-transfer metrics; they should not be read as
forgetting metrics.

## How To Run

From the repository root:

```bash
python -m zoology.launch zoology/experiments/rmt_mqar/continual_vocab.py --gpus 1
```

With Comet enabled, each model is logged as a separate experiment named:

```text
attention-continual-vocab
base_rmt-continual-vocab
fast_memory_rmt-continual-vocab
```

## How To Interpret Results

For a useful continual-learning comparison, first check whether each model can
learn the current stage at all. If current-stage accuracy is near random, then
forgetting metrics are not yet meaningful.

For the default setup, each stage has `values_per_stage = 128`, so random
query accuracy is roughly:

```text
1 / 128 = 0.0078125
```

If stage accuracy is around `0.008`, the model is essentially guessing. In that
case, do not conclude that one memory architecture is better for continual
learning yet. First make the task easier or train longer until at least the
single-stage/current-stage setting learns.

Useful calibration changes:

```text
decrease values_per_stage
decrease vocab_size
decrease random distractors
increase train examples per stage
increase max_epochs
increase d_model or n_layers
lower learning rate if losses spike after stage changes
```

## Difference From Static MQAR Sweeps

`capacity_sweep.py` and `context_sweep.py` create separate independent training
runs for each model/task setting. Those runs do not preserve weights across
task difficulties.

`continual_vocab.py` preserves weights across stages inside a single run:

```text
static sweep:
  run A trains from scratch on difficulty A
  run B trains from scratch on difficulty B

continual vocab:
  same model trains stage 0, then stage 1, then stage 2, then stage 3
```

That is the important distinction for continual learning.

## Current Limitations

- `continual_vocab.py` is vocab-growth continual MQAR only.
- Distractor-growth continual MQAR is not implemented yet.
- Near-duplicate keys and conflicting/reassigned values are not implemented in
  this config.
- The default Fast Memory RMT resets fast memory every batch, so it is not yet a
  persistent cross-batch memory experiment.
- The default config is intentionally small. It is a starting point, not a tuned
  benchmark.

## Class-Incremental Associative Retrieval

`class_incremental_ar.py` adds a separate task closer to incremental CIFAR.
Instead of only changing stage-local vocab ranges, each stage introduces a fixed
block of key/value association classes. Training samples only the current stage,
while testing uses stage-local `eval_mode="current"` splits. Averaging those
stage-local splits gives a class-balanced seen-stage score while preserving
per-stage plasticity, BWT, and forgetting measurements.

The generator is `ClassIncrementalARConfig` in
`zoology/data/class_incremental_ar.py`.

```text
stage 0 train: associations 0..15
stage 0 test:  associations 0..15

stage 1 train: associations 16..31
stage 1 test:  associations 16..31

stage 2 train: associations 32..47
stage 2 test:  associations 32..47
```

The class-incremental score after stage `t` is `continual/seen_avg_accuracy`,
the mean of stage-local accuracies for stages `0..t`. This avoids treating a
cumulative-prefix test as if it were a pure current-stage plasticity probe.

`class_incremental_ar.py` enables `evaluate_future_stages=True`, so its logs
include pre-learning/FWT metrics in addition to plasticity, BWT, and forgetting.

## Class-Incremental Horizon And Interference

`class_incremental_ar_horizon.py` runs the same class-incremental AR task with
more stages, currently 5, 10, and 20. This stresses loss of plasticity over a
longer training horizon. Interpret a drop in `continual/plasticity` or
`continual/current_stage_accuracy` as possible loss of plasticity; interpret a
drop in old-stage accuracy after it was learned as forgetting or negative BWT.

`class_incremental_ar_interference.py` adds repeated-key interference with three
variants:

```text
no_conflict_latest: no repeated keys, latest-value target
repeated_key_latest: repeated keys with changed values, target latest value
repeated_key_old: repeated keys with changed values, target original value
```

This separates ordinary class-incremental retention from overwrite behavior.
Latest-value targets test whether memory can update associations; old-value
targets test whether the model can preserve the earlier association despite a
later conflicting value.
